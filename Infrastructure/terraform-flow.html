Phase 0 Initialization & Provider Setup

Before any plan or apply, terraform init reads provider.tf and downloads required provider plugins.

provider.tf

terraform {
  required_version = ">= 1.5"              # Enforces minimum Terraform CLI version

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"                   # Any 5.x version
    }
    kubernetes = {
      source  = "hashicorp/kubernetes"
      version = "~> 2.25"
    }
    helm = {
      source  = "hashicorp/helm"
      version = "~> 2.12"
    }
    tls = {
      source  = "hashicorp/tls"
      version = "~> 4.0"
    }
  }
}

provider "aws" {
  region = var.region                       # "us-east-1" from terraform.tfvars
}
Why: Downloads provider plugins into .terraform/. Version constraints (~> 5.0) prevent breaking changes from new major versions. The AWS provider uses credentials from ~/.aws/credentials or environment variables.

Why each value matters:
  • /16 CIDR — gives 65K IPs, enough room for multiple subnets and future growth

  • Min 1 / Max 2 — keeps costs low while allowing some autoscaling
  • 7 repositories — one ECR repo per microservice

Step 1 VPC Module — Network Foundation

Runs first. No dependencies on other modules.

module "vpc" {
  source               = "./modules/vpc"
  vpc_name             = var.vpc_name             # "EKS-Demo-VPC"
  cidr_block           = var.vpc_cidr             # "10.1.0.0/16"
  public_subnet_cidrs  = var.public_subnet_cidrs
  private_subnet_cidrs = var.private_subnet_cidrs
  availability_zones   = var.availability_zones
  cluster_name         = var.cluster_name         # For subnet tagging
}

1.1 — VPC

resource "aws_vpc" "vpc" {
  cidr_block           = var.cidr_block           # "10.1.0.0/16"
  enable_dns_support   = true
  enable_dns_hostnames = true
}
Why: The isolated network. enable_dns_support + enable_dns_hostnames are required for EKS — the API server and nodes need to resolve each other by hostname.

1.2 — Internet Gateway

resource "aws_internet_gateway" "igw" {
  vpc_id = aws_vpc.vpc.id
}
Why: Connects the VPC to the public internet. Without this, nothing in the VPC can reach the outside world. Public subnets route through this.

1.3 — Public Subnets (x3)

resource "aws_subnet" "public" {
  count                   = length(var.public_subnet_cidrs)   # 3
  vpc_id                  = aws_vpc.vpc.id
  cidr_block              = var.public_subnet_cidrs[count.index]
  availability_zone       = var.availability_zones[count.index]
  map_public_ip_on_launch = false

  tags = {
    "kubernetes.io/role/elb"                    = "1"
    "kubernetes.io/cluster/${var.cluster_name}" = "owned"
  }
}
Why: 3 public subnets across 3 AZs. The kubernetes.io/role/elb tag is critical — the AWS Load Balancer Controller uses it to discover which subnets to place internet-facing ALBs in. Without this tag, Ingress resources won't get load balancers.

1.4 — Public Route Table

resource "aws_route_table" "public" {
  vpc_id = aws_vpc.vpc.id
  route {
    cidr_block = "0.0.0.0/0"                  # All non-VPC traffic...
    gateway_id = aws_internet_gateway.igw.id   # ...goes to the IGW
  }
}

resource "aws_route_table_association" "public" {
  count          = length(aws_subnet.public)
  subnet_id      = aws_subnet.public[count.index].id
  route_table_id = aws_route_table.public.id
}
Why: Makes the public subnets actually public. Without this route, traffic would stay inside the VPC even with an IGW attached.

1.5 — NAT Gateway (single AZ)

resource "aws_eip" "nat" {
  domain = "vpc"
}

resource "aws_nat_gateway" "nat" {
  allocation_id = aws_eip.nat.id
  subnet_id     = aws_subnet.public[0].id      # Lives in first public subnet
  depends_on    = [aws_internet_gateway.igw]
}
Why: Lets private subnets reach the internet (pull Docker images, download packages) without being directly reachable from outside. Single NAT Gateway saves cost — production would have one per AZ for HA.

1.6 — Private Subnets (x3)

resource "aws_subnet" "private" {
  count             = length(var.private_subnet_cidrs)   # 3
  vpc_id            = aws_vpc.vpc.id
  cidr_block        = var.private_subnet_cidrs[count.index]
  availability_zone = var.availability_zones[count.index]

  tags = {
    "kubernetes.io/role/internal-elb"           = "1"
    "kubernetes.io/cluster/${var.cluster_name}" = "owned"
  }
}
Why: EKS worker nodes run here — no public IP, no direct internet access. The internal-elb tag tells the LB controller to use these for service-to-service internal load balancers.

1.7 — Private Route Table

resource "aws_route_table" "private" {
  vpc_id = aws_vpc.vpc.id
  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.nat.id    # Outbound goes through NAT
  }
}
Why: Routes outbound traffic from private subnets through NAT. Nodes can pull images but nothing from the internet can initiate a connection to them.
VPC Module: 15 resources (1 VPC, 1 IGW, 6 subnets, 2 route tables, 6 RT associations, 1 EIP, 1 NAT GW)

Step 2 ECR Module — Container Registry & OIDC

Runs in parallel with VPC — no dependency between them. ECR is a standalone AWS service.

module "ecr" {
  source       = "./modules/ecr"
  repositories = var.repositories    # 7 service names
  github_org   = var.github_org      # "gitcliff"
  github_repo  = var.github_repo     # "microservices-devops-stack"
}

2.1 — ECR Repositories (x7)

resource "aws_ecr_repository" "repos" {
  for_each = toset(var.repositories)        # Creates one repo per service

  name         = each.value                 # "auth", "frontend", etc.
  force_delete = true                       # Can destroy even with images inside

  image_scanning_configuration {
    scan_on_push = true                     # AWS scans every pushed image for CVEs
  }

  image_tag_mutability = "IMMUTABLE"        # Tags can NEVER be overwritten
}
Why: IMMUTABLE tags prevent pushing a different image under the same tag — critical for supply chain security. scan_on_push gives a second layer of CVE scanning alongside Trivy in CI.

2.2 — GitHub Actions OIDC Provider

resource "aws_iam_openid_connect_provider" "github" {
  url             = "https://token.actions.githubusercontent.com"
  client_id_list  = ["sts.amazonaws.com"]
  thumbprint_list = [
    "6938fd4d98bab03faadb97b34396831e3780aea1",
    "1c58a3a8518e8759bf075b76b750d4f2df264fcd",
  ]
}
Why: Registers GitHub Actions as a trusted identity provider in AWS. When a workflow runs, GitHub issues an OIDC JWT. This tells AWS: "I trust tokens from GitHub." The thumbprints verify the TLS certificate chain. client_id = sts.amazonaws.com means the token's audience claim must match.

2.3 — Trust Policy (Who can assume the role)

data "aws_iam_policy_document" "github_actions_assume_role" {
  statement {
    effect  = "Allow"
    actions = ["sts:AssumeRoleWithWebIdentity"]

    principals {
      type        = "Federated"
      identifiers = [aws_iam_openid_connect_provider.github.arn]
    }

    condition {                                 # Verify token audience
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:aud"
      values   = ["sts.amazonaws.com"]
    }

    condition {                                 # Restrict to specific repo + branch
      test     = "StringLike"
      variable = "token.actions.githubusercontent.com:sub"
      values   = ["repo:gitcliff@46714226/microservices-devops-stack@1382059702:ref:refs/heads/main"]
    }
  }
}
Why: The critical security boundary. The sub claim identifies which repo and branch the workflow runs from. This restricts role assumption to only the main branch of only this specific repo. No other repo, no fork, no other branch can assume this role.

2.4 — IAM Role + Permissions Policy

resource "aws_iam_role" "github_actions_ecr_push" {
  name               = "github-actions-ecr-push"
  assume_role_policy = data.aws_iam_policy_document.github_actions_assume_role.json
}

data "aws_iam_policy_document" "ecr_push" {
  statement {
    sid       = "ECRGetAuthToken"
    actions   = ["ecr:GetAuthorizationToken"]
    resources = ["*"]                        # Auth token is account-wide (AWS limitation)
  }
  statement {
    sid     = "ECRPushPull"
    actions = [
      "ecr:BatchCheckLayerAvailability",  # Check if layers exist (dedup)
      "ecr:BatchGetImage",               # Pull manifests
      "ecr:CompleteLayerUpload",          # Finish layer upload
      "ecr:GetDownloadUrlForLayer",       # Presigned download URL
      "ecr:InitiateLayerUpload",          # Start layer upload
      "ecr:PutImage",                     # Push final manifest
      "ecr:UploadLayerPart",              # Upload layer chunk
    ]
    resources = [for repo in aws_ecr_repository.repos : repo.arn]
                                                # Scoped to only the 7 repos
  }
}
Why: Defines WHAT the role can do. Push/pull actions are scoped to only the 7 ECR repo ARNs — the role can't touch any other repos in the account. Principle of least privilege.
ECR Module: 10 resources (7 repos, 1 OIDC provider, 1 IAM role, 1 role policy)

Step 3 EKS Module — Kubernetes Cluster

Waits for VPC to complete — needs private_subnet_ids.

module "eks" {
  source     = "./modules/eks"
  subnet_ids = module.vpc.private_subnet_ids   # Workers go in private subnets
  depends_on = [module.vpc]
  ...
}

3.1 — Cluster IAM Role

resource "aws_iam_role" "eks_cluster_role" {
  name = "${var.cluster_name}-cluster-role"
  assume_role_policy = jsonencode({
    Statement = [{
      Effect    = "Allow"
      Principal = { Service = "eks.amazonaws.com" }
      Action    = "sts:AssumeRole"
    }]
  })
}
Why: The EKS control plane is an AWS-managed service. It needs an IAM role to manage resources on your behalf (ENIs, security groups). The trust policy allows only the EKS service to assume it.

3.2 — EKS Cluster

resource "aws_eks_cluster" "eks" {
  name     = var.cluster_name                  # "eks-cluster"
  role_arn = aws_iam_role.eks_cluster_role.arn
  version  = "1.31"                            # Kubernetes version

  vpc_config {
    subnet_ids              = var.subnet_ids
    endpoint_public_access  = false             # API NOT reachable from internet
    endpoint_private_access = true              # API reachable from within VPC only
  }

  encryption_config {
    resources = ["secrets"]                    # Encrypt K8s Secrets at rest
    provider {
      key_arn = aws_kms_key.eks_secrets.arn    # Customer-managed KMS key
    }
  }
}
Why: endpoint_public_access = false is security hardening — the K8s API is only accessible from within the VPC. encryption_config encrypts Secrets in etcd. Without it, Secrets are stored as base64 (readable, not encrypted).

3.3 — KMS Key for Secrets Encryption

resource "aws_kms_key" "eks_secrets" {
  description             = "KMS key for EKS secrets encryption"
  deletion_window_in_days = 7                # Safety window before permanent deletion
  enable_key_rotation     = true             # Auto-rotates annually
}
Why: Customer-managed key with auto-rotation. The 7-day deletion window prevents accidental permanent loss of the key (and all encrypted Secrets).

3.4 — EKS OIDC Provider (for IRSA)

data "tls_certificate" "eks" {
  url = aws_eks_cluster.eks.identity[0].oidc[0].issuer
}

resource "aws_iam_openid_connect_provider" "eks" {
  client_id_list  = ["sts.amazonaws.com"]
  thumbprint_list = [data.tls_certificate.eks.certificates[0].sha1_fingerprint]
  url             = aws_eks_cluster.eks.identity[0].oidc[0].issuer
}
Why: Enables IRSA (IAM Roles for Service Accounts). Kubernetes pods can assume IAM roles without storing AWS credentials. Different from the GitHub OIDC provider in the ECR module — this one is for in-cluster workloads.

3.5 — Node Group IAM Role + Policies

resource "aws_iam_role" "eks_node_role" { ... }

# Three AWS-managed policies attached:
AmazonEKSWorkerNodePolicy     # Nodes register with cluster
AmazonEKS_CNI_Policy          # VPC CNI manages pod IPs via ENIs
AmazonEC2ContainerRegistryReadOnly  # Nodes pull images from ECR
Why: Worker nodes are EC2 instances that need permissions to: join the cluster, manage network interfaces for pod networking, and pull container images. Without any of these, nodes fail to start.

3.6 — Managed Node Group

resource "aws_eks_node_group" "node_group" {
  cluster_name    = aws_eks_cluster.eks.name
  node_role_arn   = aws_iam_role.eks_node_role.arn
  subnet_ids      = var.subnet_ids             # Private subnets
  instance_types  = ["m7i-flex.large"]
  capacity_type   = "ON_DEMAND"
  disk_size       = 30

  scaling_config {
    desired_size = 1
    min_size     = 1
    max_size     = 2
  }

  update_config {
    max_unavailable = 1                      # Rolling updates: 1 node at a time
  }
}
Why: AWS manages provisioning, patching, and draining of EC2 instances. depends_on (IAM policies) ensures permissions exist before nodes try to join — otherwise they fail with access denied.

3.7 — EBS CSI Driver (IRSA)

resource "aws_iam_role" "ebs_csi_irsa" {
  assume_role_policy = ...  # Only ebs-csi-controller-sa in kube-system
}

resource "aws_eks_addon" "ebs_csi" {
  cluster_name             = aws_eks_cluster.eks.name
  addon_name               = "aws-ebs-csi-driver"
  service_account_role_arn = aws_iam_role.ebs_csi_irsa.arn
}
Why: Your PostgreSQL StatefulSet uses PersistentVolumeClaims — the EBS CSI driver dynamically provisions EBS volumes. IRSA restricts this powerful permission to only the CSI controller pod, not every pod on the node. Principle of least privilege.
EKS Module: ~14 resources (1 cluster, 1 KMS key, 1 KMS alias, 1 OIDC provider, 2 IAM roles, 4 policy attachments, 1 node group, 1 EBS CSI role, 1 EBS addon, 1 TLS cert data)

Step 4 Kubernetes & Helm Provider Configuration

After EKS is up, configure providers to talk to the cluster.

data "aws_eks_cluster_auth" "eks" {
  name = module.eks.cluster_name               # Gets a short-lived auth token
}

provider "kubernetes" {
  alias                  = "eks"
  host                   = module.eks.cluster_endpoint
  cluster_ca_certificate = base64decode(module.eks.cluster_certificate_authority_data)
  token                  = data.aws_eks_cluster_auth.eks.token
}

provider "helm" {
  alias = "eks"
  kubernetes {
    host                   = module.eks.cluster_endpoint
    cluster_ca_certificate = base64decode(...)
    token                  = data.aws_eks_cluster_auth.eks.token
  }
}
Why: Tells Terraform how to authenticate to the K8s API. The CA certificate verifies you're talking to the real API server, not a MITM. The alias = "eks" allows multiple provider configs. These are passed to ArgoCD, Monitoring, and Kyverno modules.

Step 5 ArgoCD Module — GitOps Controller

Runs after EKS. Deploys in parallel with Monitoring and Kyverno.

resource "kubernetes_namespace_v1" "argocd" {
  metadata { name = "argocd" }
}

resource "helm_release" "argocd" {
  name       = "argocd"
  repository = "https://argoproj.github.io/argo-helm"
  chart      = "argo-cd"
  version    = "7.7.5"
  timeout    = 600

  values = [yamlencode({
    server = {
      service = { type = "ClusterIP" }         # Internal only
    }
    configs = {
      params = { "server.insecure" = true }   # TLS at ingress, not here
    }
  })]
}
Why: ArgoCD watches your Git repo for changes to k8s/overlays/dev/kustomization.yaml and automatically syncs cluster state. ClusterIP = only reachable within the cluster. server.insecure = TLS terminated at the Ingress/ALB in front.
ArgoCD Module: 2 resources (1 namespace, 1 Helm release)

Step 6 Monitoring Module — Prometheus & Grafana

Runs in parallel with ArgoCD. Both depend only on EKS.

resource "helm_release" "kube_prometheus_stack" {
  chart   = "kube-prometheus-stack"
  version = "65.1.0"

  values = [yamlencode({
    prometheus = {
      prometheusSpec = {
        serviceMonitorSelectorNilUsesHelmValues = false
        podMonitorSelectorNilUsesHelmValues     = false
      }
    }
    grafana = {
      sidecar = {
        dashboards = { enabled = true, label = "grafana_dashboard" }
      }
    }
  })]
}
Why: The two critical settings:
  • serviceMonitorSelectorNilUsesHelmValues = false — Without this, Prometheus only discovers its own ServiceMonitors. Setting false means it discovers ServiceMonitors from all namespaces, including the 6 in your boutique namespace.
  • grafana.sidecar.dashboards — Auto-imports dashboards from ConfigMaps labeled grafana_dashboard.
Monitoring Module: 2 resources (1 namespace, 1 Helm release — which deploys Prometheus, Grafana, Alertmanager, and Prometheus Operator)

7.1 — Kyverno Helm Release

resource "helm_release" "kyverno" {
  chart      = "kyverno"
  version    = "3.3.4"

7.2 — SLSA Provenance ClusterPolicy

resource "kubernetes_manifest" "require_slsa_provenance" {
  depends_on = [helm_release.kyverno]          # CRDs must exist first

  manifest = {
    kind = "ClusterPolicy"
    metadata = { name = "require-slsa-provenance" }
    spec = {
      validationFailureAction = "Audit"       # Log only, don't block (initially)
      rules = [{
        name  = "verify-slsa-provenance"
        match = { resources = { kinds = ["Pod"], namespaces = ["boutique"] } }

        verifyImages = [{
          imageReferences = ["501588780081.dkr.ecr.us-east-1.amazonaws.com/*"]
          attestations = [{
            type = "https://slsa.dev/provenance/v1"
            attestors = [{
              entries = [{
                keyless = {
                  issuer  = "https://token.actions.githubusercontent.com"
                  subject = "https://github.com/gitcliff/microservices-devops-stack/*"
                  rekor   = { url = "https://rekor.sigstore.dev" }
                }
              }]
            }]
          }]
        }]
      }]
    }
  }
}
Why: When a Pod is created in boutique namespace with an ECR image, Kyverno:
  1. Fetches OCI referrer artifacts from ECR
  2. Finds the SLSA provenance attestation
  3. Verifies it was signed by GitHub Actions OIDC (Sigstore keyless)
  4. Checks the signature against the Rekor transparency log
  5. Audit mode: logs result. Enforce mode: rejects Pod if verification fails
Kyverno Module: 3 resources (1 namespace, 1 Helm release, 1 ClusterPolicy manifest)
